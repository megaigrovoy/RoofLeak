# Handoff — Roof Leak

Снимок состояния проекта для передачи контекста (новому агенту, новой сессии, другому
разработчику). Актуально на коммит `3734007` (main, синхронизирован с origin).

---

## 1. Что это за проект

Веб-игра на камере: игрок разводит руки — между запястьями появляется ведро, которым
нужно ловить капли с протекающей крыши. Поддерживает **1 или 2 игроков** перед одной
камерой. Трекинг тела — **MediaPipe Pose Landmarker** (WASM, в браузере, без бэкенда).

- **Прод:** https://roofleak.blagogames.com/
- **Репозиторий:** https://github.com/megaigrovoy/RoofLeak (ветка `main`, релиз = push в `main`)
- **Локальная копия:** `E:\BlagoGames\web-mediapipe 3 - roof leak`
- **Стек:** Vite + `@mediapipe/tasks-vision` (Pose Landmarker). Один файл [`main.js`](../main.js)
  (~3700 строк) — весь код игры, без фреймворка.

### Запуск

```bash
npm install
npm run dev      # HTTPS — камере нужен secure context
npm run build     # прод-сборка в dist/
npm run preview
```

`npm run dev`/`build` сначала гоняют `prepare:wasm` ([scripts/copy-mediapipe-wasm.mjs](../scripts/copy-mediapipe-wasm.mjs)),
который копирует WASM-рантайм MediaPipe в `public/mediapipe-wasm/` для same-origin раздачи
(с CDN-фолбэком на jsDelivr, см. `initializeModels()` в `main.js`).

### Деплой

Прямого пайплайна в репозитории не видно — судя по истории, `git push origin main` тянет
за собой деплой на `roofleak.blagogames.com` (внешний CI/хостинг, не часть этого репо).
После пуша **прод обновляется автоматически** — это подтверждено в этой сессии (хэш бандла
на проде совпадал с локальной сборкой сразу после пуша).

## 3. Трекинг двух игроков — история этой сессии и текущее состояние

Это было основной темой работы. MediaPipe `PoseLandmarker` **не даёт стабильных track ID**
между кадрами — вся стабильность (`Pose#0`/`Pose#1`) реализована вручную в
`bindStablePoseKeys()` (~main.js:3130).

### Хронология фиксов (в порядке коммитов)

1. **`fac85ac` / `8474cad` — constant-velocity предсказание.**
   Матчинг детекций к позиции трека происходил по последней наблюдённой точке, что давало
   ID-swap при пересечении игроков. Добавлено предсказание движения (центр плеч, EMA
   скорости). Первая версия была слишком агрессивной (горизонт 500мс, без потолка скорости)
   и **сломала прод** — второй игрок начал часто пропадать. Откручено до консервативных
   параметров: горизонт 50мс, потолок скорости 4px/мс, сброс скорости после паузы >200мс.
   **Урок:** предсказание должно быть заметно только в узком окне неопределённости, не
   доминировать над наблюдением.

2. **`c36265d` — track lifecycle + цветовая подпись.** Настоящая причина «второй игрок
   постоянно пропадает» — трек **выбрасывался целиком**, как только видна только одна поза
   (`stablePoseShoulderMid = [best]`). Переписано на реестр треков: `predict → cost matrix →
   assign → age out`. Треки при потере не удаляются, а живут `TRACK_MAX_AGE_MS = 2000мс` как
   `lost`, предсказываясь по последней скорости. Плюс — цветовая подпись торса (ROI
   плечи+бёдра, сэмплится из оффскрин-канваса 64×48, EMA) как второе слагаемое в cost —
   помогает не перепутать игроков после долгой окклюзии. Проверено 8 симулированными
   сценариями (`bindStablePoseKeys` логика без DOM) — все проходят.

3. **`7d50e2a` — рука у края экрана не должна гасить всё ведро.** Видимость проверялась
   как `Math.min` по всем 4 точкам (2 запястья + 2 плеча) — одна рука у края кадра роняла
   **обе** руки и ведро. Исправлено: руки проверяются по отдельности; потерянная (реально
   ушедшая за кадр) достраивается «призраком» — последним известным смещением от центра
   плеч. Обязательны только плечи. Десктопу заодно добавлен небольшой grace (250мс, был 0).

4. **`4dce096` / `3734007` — кулаки визуально путались и дёргались.** Три отдельные причины,
   все найдены и исправлены в одном заходе:
   - **Рывки:** точки запястий шли в отрисовку без второго слоя сглаживания, который есть у
     ведра (`smoothBucketDisplay`). Добавлено — но с **отдельной, более быстрой альфой**
     (`WRIST_DISPLAY_SMOOTH_ALPHA = 0.45`), иначе каскад из двух медленных EMA давал лаг
     кулаков за реальными руками при быстром движении.
   - **Путаница/резкие подмены:** пара запястий сопоставлялась предыдущему кадру «по
     ближайшему расстоянию», а руки в этой игре почти всегда близко (держат ведро) — суммы
     straight/crossed почти равны, назначение дребезжало. Заменено на сортировку по
     экранному X (левый/правый на экране) — стабильно, пока руки не почти в одной точке;
     на пересечении передача бесшовная.
   - **Кулак не на уровне настоящей руки:** «призрак» из пункта 3 включался слишком рано
     (порог видимости 0.45 — обычная просадка при быстром движении, а не реальная потеря
     руки). Теперь призрак включается только если лендмарк **вне рамки кадра** (±5%) или
     видимость почти нулевая (`WRIST_GHOST_VISIBILITY = 0.15`). Рука в кадре с так себе
     confidence использует свою настоящую координату.

### Ключевые константы трекинга (main.js)

```js
// Предсказание движения (constant-velocity), ~main.js:3088
POSE_VELOCITY_SMOOTH_ALPHA = 0.35
POSE_PREDICT_MAX_MS        = 50    // короткий горизонт — ~1 кадр камеры
POSE_VELOCITY_MAX_PX_MS    = 4     // потолок скорости
POSE_VELOCITY_STALE_MS     = 200   // после паузы скорость сбрасывается

// Track lifecycle, ~main.js:3130
TRACK_MAX_AGE_MS           = 2000  // трек живёт как lost до удаления
TRACK_MAX_MATCH_DIST_MUL   = 0.55  // порог назначения, доля minSide экрана
TRACK_SWAP_HYSTERESIS      = 12    // гистерезис против дребезга straight/crossed

// Цветовая подпись торса, ~main.js:3155
TORSO_SAMPLE_W/H           = 64×48 // оффскрин-канвас
TORSO_COLOR_SMOOTH_ALPHA   = 0.15
TORSO_COLOR_COST_MUL       = 0.5
TORSO_COLOR_MAX_COST       = 140   // потолок вклада цвета в cost

// Руки/ведро, ~main.js:990
WRIST_SMOOTH_ALPHA          = 0.24  // EMA сырых запястий
WRIST_DISPLAY_SMOOTH_ALPHA  = 0.45  // EMA кулаков-спрайтов (быстрее, чем у ведра)
BUCKET_DISPLAY_SMOOTH_ALPHA = 0.2   // EMA положения ведра (медленнее — плавность)
WRIST_TELEPORT_PX           = 38    // порог, выше которого точка не сглаживается, а телепортируется
WRIST_GHOST_VISIBILITY      = 0.15  // ниже — рука считается потерянной даже в кадре
GAME_CFG.wristMinVisibility = 0.45  // десктопный порог «нормальной» видимости
```

Мобильный профиль (`buildTrackTuning()`, ~main.js:1005) переопределяет часть порогов ниже
(например `wristMinVisibility: 0.3`) и добавляет `bucketGraceMs: 600` — на Android трекинг
шумнее, поэтому терпимее к просадкам уверенности.

### Что НЕ реализовано (сознательно отложено)

- **Пункт C плана** (псевдо-глубина из ширины плеч в cost-matrix) — не понадобился, есть
  в чек-листе `two-player-occlusion-tracking.md`. Добавлять, если после наблюдения на проде
  выяснится, что «задний» игрок при перекрытии крадёт ID «переднего».
- **Миграция на MoveNet MultiPose** — осознанно отклонена сейчас (см.
  `movenet-migration-assessment.md`). Главный риск — придётся заново проходить
  Android-калибровку, аналогичную `mobile-tracking-fix.md`, но для другого рантайма.
  Возвращаться к вопросу, если понадобится **3+ игроков** (наш трекер держит максимум 2,
  ветка `items.length >= 3` просто раздаёт ключи по порядку без трекинга).
- Тесты трекинга в этой сессии — **симуляция логики** (Node-скрипт, копия
  `bindStablePoseKeys` без DOM/MediaPipe), не прогон на реальной камере. Живой прод-тест
  после каждого фикса подтверждался пользователем вручную.

## 4. Известные грабли / что учитывать при следующих изменениях

- **Не трогайте выбор CPU/GPU делегата на мобильных** без перечитывания
  `mobile-tracking-fix.md` — это не оптимизация, а обход конкретного Android-бага
  (неправильная ориентация кадра при GPU-загрузке текстуры).
- **`bindStablePoseKeys` вызывается каждый render-кадр**, но реальные данные обновляются
  только на новый кадр камеры (`poseFrameIsNew`/`isNewFrame`). Любая новая логика внутри
  должна учитывать этот gate — иначе скорость/сглаживание будут «прокручиваться» лишний раз
  на быстрых экранах (120 Гц) относительно ~30 fps камеры.
- **Каскад EMA — частый источник лага.** Если добавляете новый слой сглаживания поверх
  уже сглаженной величины, либо используйте более быструю альфу для него, либо не
  сглаживайте дважды — см. историю фикса кулаков (§3.4) как прецедент.
- **`visibility` MediaPipe — шумный сигнал**, особенно при быстром движении; не стоит
  использовать единый жёсткий порог для «рука потеряна» вообще везде — для разных целей
  (ведро vs визуальный кулак vs призрак-реконструкция) сейчас разные пороги, и это осознанно.
- Формат ключей игроков — строго `Pose#0` / `Pose#1` (regex в `playerIndexFromPoseKey`).
  Если меняете схему треков, не ломайте этот формат — от него зависит счёт/вода/HUD на игрока.

## 5. Возможные следующие шаги (не начаты)

- Живой прод-тест сценария «два игрока активно пересекаются» — проверить, не нужен ли
  всё-таки пункт C (псевдо-глубина).
- Если понадобится **3–4 игрока** — начинать с оценки MoveNet заново (документ есть, но
  писался под условие "2 игрока достаточно").
- Геймдизайн-меры против окклюзии, предложенные в ресёрче (`two-player-tracking-research.md`
  §4.3): подсказка «встаньте на расстоянии», разметка зон на экране — не реализованы,
  это дешёвая мера, если алгоритмических фиксов не хватит.

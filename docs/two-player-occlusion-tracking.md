# Трекинг двух игроков и устойчивость к окклюзии

Документ описывает: (1) как сейчас устроен трекинг двух игроков и трекаются ли руки
отдельно; (2) полный список подходов к сохранению стабильных ID при пересечении игроков
(один загораживает другого), включая SOTA 2025/2026; (3) выбранный план интеграции
и обоснование, почему он лучший для этого проекта.

---

## 1. Как сделано сейчас

Вся логика — в [`main.js`](../main.js). MediaPipe `PoseLandmarker` **не выдаёт стабильных
track ID**: на каждом кадре он возвращает массив поз в произвольном порядке. Стабильность
«Игрок 0 / Игрок 1» реализована вручную.

Цепочка:

1. **Детекция** — `createPoseLandmarkerInstance()` (`main.js:1947`), `numPoses = 1|2`.
   На мобильных принудительно CPU-делегат (см. [mobile-tracking-fix.md](./mobile-tracking-fix.md)).
2. **Первичная сортировка** — `getOrderedPersons()` (`main.js:3055`): позы сортируются по
   средней X-координате запястий (левее → `Pose#0`, правее → `Pose#1`).
3. **Стабилизация ID во времени** — `bindStablePoseKeys()` (`main.js:3084`), ядро трекинга.
   Хранит `stablePoseShoulderMid` — центры плеч (midpoint лендмарков 11/12) с прошлого кадра.
   Ассоциация по **ближайшему центру плеч**; для 2 игроков сравнивает
   `straight = d00+d11` vs `crossed = d01+d10` и берёт меньшее с гистерезисом `+12px`
   (`main.js:3173`) — по сути вырожденный венгерский алгоритм для N=2.
4. **Grace-удержание** — `holdBucketDuringGrace()` (`main.js:3194`): при потере трекинга
   ведро держится на месте до `bucketGraceMs` (600 мс mobile).
5. **Сглаживание** — EMA по запястьям/плечам/ведру + телепорт-порог против рывков.

### Трекаются ли руки отдельно?

**Нет.** Отдельного `HandLandmarker` / `GestureRecognizer` в проекте нет (grep по
`HandLandmarker|numHands|handedness` — 0 совпадений). «Руки» — это просто **два запястья
из позы**: лендмарки `15` (левое) и `16` (правое). Ведро строится из них в
`computeBucket()` (`main.js:2929`): центр = середина между запястьями, ширина = от ширины
плеч, угол = вектор между запястьями.

Следствие для окклюзии: **отдельного трека рук, который мог бы «пережить» окклюзию тела,
нет.** Как только поза игрока теряется под перекрытием, пропадают и его запястья — держать
нечего, кроме grace-заморозки последнего ведра. Значит, вся устойчивость обязана жить на
уровне **ассоциации поз**, а не рук.

### Слабые места при окклюзии

- Ассоциация только по **2D-центроиду плеч**: при сближении `d00≈d01`, `d10≈d11` → суммы
  почти равны → гистерезиса `+12px` не хватает → **swap ID** (счёт/вода уходят не тому).
- **Нет модели движения**: ID присваивается по абсолютной близости, а не по предсказанию,
  куда игрок двигался → крест-накрест расхождение путает игроков.
- **Нет appearance-признаков**: двух людей нельзя различить после долгой окклюзии.
- При перекрытии `numPoses=2` часто отдаёт **одну** позу → второй «замирает» в grace, а его
  ID на выходе может достаться не тому.

## 2. Все варианты решения

Ранжировано по «эффект / трудозатраты» для браузерного real-time на 2 игрока.

| # | Подход | Что чинит | Стоимость | Зависимости |
|---|--------|-----------|-----------|-------------|
| 1 | **Kalman / constant-velocity** — матч к предсказанию, а не к прошлой позиции (ядро SORT). Во время окклюзии экстраполирует траекторию. | Крест-накрест swap, ID после выхода из окклюзии | ~50 строк | нет |
| 2 | **Венгерский алгоритм** на cost-matrix — обобщение `straight/crossed`; место, где смешать сигналы (dist Махаланобиса + Δплечи + appearance) | Устойчивость когда центроиды почти совпали | малая | нет |
| 3 | **Appearance / Re-ID**. Дёшево: цветовая гистограмма/средний цвет торса (ROI плечи+бёдра). Тяжело: Re-ID CNN эмбеддинг (DeepSORT). Считать по уверенным кадрам. | Крест-накрест после долгой окклюзии | дёш. малая / CNN тяжело | нет / +модель |
| 4 | **Каскадная ассоциация + track lifecycle** (ByteTrack): сначала уверенные детекции, потом слабые; трек tentative→confirmed→lost N кадров с предсказанием | Полузакрытый игрок не выбрасывается; меньше мерцаний | малая | нет |
| 5 | **Pseudo-depth** (PD-SORT 2025): кто ближе к камере детектируется надёжнее. Псевдо-глубину оценить по `shoulderW` (уже считается) | «Задний» не крадёт ID у «переднего» | тривиальная | нет |
| 6 | **GM-PHD probabilistic multi-target** | Окклюзия вероятностно | высокая | overkill |
| 7 | **Transformer track-query** (TGFormer AAAI: Track Query Group + Occlusion-Aware Memory-Attention; TransTrack/TrackFormer) | Окклюзия через attention/память | очень высокая | тяжёлая модель — не для браузера |
| 8 | **VeTrack 2026** — confidence-guided multi-level association (адаптивный матчинг по confidence бокса) | Полузакрытый игрок; окклюзия в потоке | средняя | transformer-appearance опционален |
| 9 | **Продакшн-трекеры 2026**: OC-SORT / ByteTrack портированы на JS + ONNX Runtime Web (WASM в табе). BoT-SORT-ReID слишком тяжёл для браузера 2026 → motion-only предпочтителен | Готовые SOTA-ядра под окклюзию | средняя | ONNX Runtime Web |
| 10 | **Norfair** (Tryolabs) — лёгкий кастомизируемый трекер, альтернатива ByteTrack | Референс минимальной реализации | — | Python-библиотека |

Ключевой факт 2026: **BoT-SORT-ReID (appearance) официально признан слишком тяжёлым для
браузерного железа** → в браузере предпочтительны **motion-only трекеры (OC-SORT / ByteTrack)**.

## 3. Выбранный план интеграции

> **Компактный OC-SORT-подобный трекер поверх центра плеч, целиком внутри
> `bindStablePoseKeys`, без новых зависимостей.**
> = пункты **1 + 2 + 5** списка, плюс лёгкий приём из **4/8**. Пункты 3(CNN)/6/7/9(ONNX)
> сознательно НЕ берём.

### Что конкретно делаем

**A. Kalman / constant-velocity на центр плеч (замена «straight vs crossed»)**
Для каждого стабильного трека (`Pose#0`, `Pose#1`) хранить состояние
`{x, y, vx, vy}` центра плеч. Каждый кадр:
1. **Predict**: `x += vx*dt; y += vy*dt` (dt — по таймстампу нового кадра камеры,
   у нас сглаживание и так привязано к новому кадру, см. mobile-tracking-fix.md).
2. **Associate**: матчить текущие детекции к **предсказанным** позициям, не к прошлым.
3. **Update**: скорректировать состояние наблюдением (EMA-упрощение Калмана достаточно).

**B. Cost-matrix + венгерский (для N=2 — тот же перебор 2×2, но расширяемый)**
Стоимость пары (трек ↔ детекция):
```
cost = w_dist * dist(predicted, detection)      // A
     + w_shoulder * |ΔshoulderWidth|            // масштаб/стать
     + w_depth * |Δpseudo_depth|                // E, псевдо-глубина из shoulderW
```
Матч = минимальная сумма (для 2 игроков — сравнение straight/crossed, но теперь по
predicted-позиции и с несколькими сигналами). Гистерезис сохраняем.

**C. Pseudo-depth из `shoulderW`**
`shoulderW` уже сглажена (`smoothShoulderWidth`). Больше плечи ≈ ближе к камере. Кладём
`|Δdepth|` в cost — «задний» (меньшие плечи, чаще перекрыт) не крадёт ID «переднего».

**D. Observation-centric восстановление (суть OC-SORT) + lifecycle**
Пока игрок под окклюзией — трек не удаляется, **предсказывается** Калманом (не просто
grace-заморозка ведра). При повторном появлении матчим детекцию к предсказанной, а не к
«замороженной» позиции → корректный ID после длинной окклюзии. Grace (`bucketGraceMs`)
остаётся для рендера ведра, но теперь опирается на предсказанное состояние.

**E. (опционально, дёшево) 1 appearance-снимок торса**
Средний цвет / мини-гистограмма ROI между плечами и бёдрами, снятая при высокой видимости.
Добавляется как ещё одно слагаемое cost только когда движение неоднозначно. Всё на CPU,
без модели. Включать, если после A–D всё ещё случаются swap при долгой полной окклюзии.

### Что сохраняем без изменений
- Формат ключей `Pose#0` / `Pose#1` и `playerIndexFromPoseKey`.
- `stablePoseShoulderMid` (расширяется полями `vx, vy, depth`, опц. `color`).
- Grace-рендер ведра, EMA-сглаживание, CPU-делегат на мобильных.

## 4. Почему этот вариант лучший

1. **Бьёт точно в корневую причину.** Swap при окклюзии возникает из-за ассоциации по
   *текущей* позиции без учёта движения. Kalman/OC-SORT-логика (A, D) устраняет именно это —
   ID следует за траекторией, а не за случайной близостью.
2. **Подтверждён практикой 2026 для браузера.** Обзор продакшн-MOT прямо говорит: appearance/
   ReID-CNN (BoT-SORT-ReID, DeepSORT, трансформеры) **слишком тяжелы для браузера**, а
   **motion-only OC-SORT/ByteTrack — предпочтительный выбор**. Мы берём именно motion-only ядро.
3. **Ноль новых зависимостей, real-time.** ~50–100 строк внутри существующей функции. Не тянем
   ONNX Runtime Web (вариант 9), не грузим CNN (3), не ставим Python-Norfair (10). Важно для
   слабых мобильных, где мы и так ушли на CPU-делегат.
4. **Переиспользует то, что уже считается.** `shoulderW` уже сглажена → псевдо-глубина (C/E)
   бесплатна. Сглаживание уже привязано к новому кадру камеры → dt для Калмана корректен.
5. **Инкрементально и без риска.** A→B→C→D включаются по очереди; каждый шаг тестируется на
   сцене «игроки сходятся/расходятся»; E — только если понадобится. Формат ID и grace не ломаются.
6. **Тяжёлые SOTA-идеи забраны в дешёвой форме.** Multi-level association (ByteTrack/VeTrack) →
   как «матчить слабую детекцию отдельно/не выбрасывать»; memory под окклюзию (TGFormer) → как
   1 appearance-снимок торса (E). Получаем суть без стоимости трансформера.

### Отклонённые варианты — коротко
- **CNN Re-ID / трансформеры (3-CNN, 7, 9-ONNX):** за бюджетом браузера 2026; несоразмерны
  задаче на 2 фиксированных игрока.
- **GM-PHD (6):** академический аппарат для переменного числа целей — у нас ровно 2.
- **Norfair (10):** Python, не для web-рантайма; полезен лишь как референс.

## 5. Порядок внедрения (чек-лист)

- [x] A. **Constant-velocity предсказание** — `predictedShoulderMid` / `updateStableTrack`.
      Матч к предсказанию, скорость (EMA) обновляется только на новом кадре камеры.
      Консервативные настройки: горизонт 50мс, потолок скорости 4px/мс, сброс после паузы >200мс.
- [x] B. **Cost-matrix** — `trackMatchCost(track, item)` = расстояние до предсказания +
      цветовая подпись; 2×2 сравнение straight/crossed + гистерезис `TRACK_SWAP_HYSTERESIS`.
- [x] D. **Track lifecycle** — треки НЕ удаляются при потере: живут как `lost` до
      `TRACK_MAX_AGE_MS` (2000мс), `dropExpiredTracks` чистит истёкшие, `freePoseKey` выдаёт
      свободный `Pose#N`. **Это лечило баг «второй игрок постоянно пропадает»** — раньше его
      трек просто выбрасывался.
- [x] E. **Цветовая подпись торса** — `sampleTorsoColor` (ROI плечи+бёдра из оффскрин-канваса
      64×48), `updateTrackColor` (EMA), `torsoColorCost` — слагаемое в стоимость матча.
      Восстанавливает identity после окклюзии без нейросети.
- [ ] C. Псевдо-глубина из `shoulderW` — **не реализовано** (пока не понадобилось; добавляется
      слагаемым в `trackMatchCost`, если после прод-теста задний игрок будет красть ID переднего).
- [x] Тесты: 8 сценариев (мелькание, окклюзия 600мс, истечение maxAge, пересечение крест-накрест,
      цветовое различение, одиночный игрок, пустой кадр) — все проходят.
- [x] Оценка миграции на MoveNet — см. [movenet-migration-assessment.md](./movenet-migration-assessment.md)
      (вердикт: **не мигрировать сейчас**; вернуться к вопросу при >2 игроков).
